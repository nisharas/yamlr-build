## The "Can't-Solve-Yourself" Manifesto

Yamlr exists to fix the problems that humans and today's tools cannot safely solve themselves. When you have thousands of Kubernetes manifests—many generated by Helm, Kustomize, or AI—the YAML is too messy, too interconnected, and too large for engineers to manually repair without missing dangerous edge cases. Traditional validators and policy engines only detect problems in already-parseable files; they choke on broken syntax and stop at red underlines. Yamlr goes deeper: it reconstructs broken YAML structure using Kubernetes schemas, repairs cross-resource relationships across Services, ConfigMaps, Secrets and Ingresses, and does it reliably at repository scale. The goal is simple: **every other tool in your stack should be able to assume "the manifests are sane" because yamlr made them that way.**

## Future-Proofing: CDK8s, Pulumi, and the "Post-YAML" Trend

CDK8s, Pulumi, and similar tools change **how** manifests are authored, but almost all still produce standard Kubernetes YAML that gets stored, reviewed, and validated. Yamlr's relevance doesn't disappear — it shifts one step downstream.

**Key facts:**
- CDK8s explicitly "produces standard Kubernetes YAML" committed to Git
- Pulumi has `kubernetes.yaml.ConfigFile/ConfigGroup` and renders objects into YAML for `kubectl` / CI/CD
- Pulumi is at 12% adoption (vs Terraform 76%) with 45% YoY growth — growing but not replacing YAML
- Clusters, GitOps tools, and validators all still operate on YAML as the intermediate representation

**Strategic response:**

| Action | How |
|:--|:--|
| **Treat them as upstream generators** | Position yamlr as: "Run *after* `cdk8s synth` / Pulumi to validate and heal generated YAML before it hits Git or the cluster" |
| **Generator-aware modes** | Flags like `--source=cdk8s` / `--source=pulumi` to tweak heuristics |
| **Integration recipes** | `cdk8s synth > out.yaml && yamlr heal out.yaml` |
| **Solve what they don't** | CDK/Pulumi focus on authoring abstractions; yamlr focuses on cross-resource graph repair when multiple generators & hand-written YAML mix |

**Mental model:** The more generators in a repo, the more glue and sanity-checking is needed at the manifest boundary — which is exactly where yamlr lives.

## Not One-and-Done: Why Yamlr Must Stay in the Flow

You only "use yamlr once and throw it away" if your manifests **stop changing** — which never happens.

**The evidence (2025):**
- **79% of K8s production outages** are from configuration and change-related issues (Komodor 2025 Enterprise Report)
- **65% of orgs** missing liveness/readiness probes
- **46% of companies** using deprecated Helm charts in ≥50% of workloads
- **44% of firms** run >71% of workloads as root
- Configuration drift is continuous: hotfixes via `kubectl`, controllers mutating resources, different Helm values per env

**Design for continuous use:**

| Touchpoint | When It Runs | Value |
|:--|:--|:--|
| **Pre-commit hook** | Every commit touching manifests | Catch issues before they hit remote |
| **CI check on every PR** | `yamlr scan` / `yamlr heal --dry-run` | Block regressions, show diffs |
| **Scheduled repo hygiene** | Weekly/monthly cron | Catch new deprecations, policy changes, cross-resource drift |

**Messaging:** The initial cleanup is the "wow" moment. The pre-commit/CI integration is why they keep yamlr installed forever.

### Mandatory Gates (from `FEATURE_SCORECARD.md`)

| Gate | Rule | Consequence |
|:--|:--|:--|
| 🔒 **Trust** | "Can this ever break prod?" Default must be safe + explainable | **Default is S1 preview for any fix that changes semantics** (security posture, limits, probes, image tags, cross-resource stubs). `--dry-run`/`--diff` always available |
| 🔒 **Comments** | Default healing preserves comments and formatting | Any fix that drops comments must be opt-in and clearly reported. YAML in ops repos carries tribal knowledge in comments |
| 🧊 **Determinism** | Same input + same version + same config ⇒ identical output | Nondeterministic ordering is a bug. GitHub code scanning flags non-deterministic SARIF generators. Critical for CI stability |
| ⚡ **Speed** | 3 modes (below) | Slow or noisy features get deferred |

**Speed gate (3 modes):**
  - Hook: <2s on changed YAML only (after warm cache, no network calls)
  - PR/CI: <30s on changed YAML + dependencies (full repo nightly)
  - Batch: throughput goal (54+ files/s), no strict time budget

## Guiding Principles

- **Healing > everything:** if a task doesn't improve healing or habit, delay it.
- **Conservative by default;** aggressive fixes are always opt-in. **S1 preview is the default for semantic changes.**
- **Depth over breadth:** prefer depth in a few capabilities over breadth across many.
- **Be the invisible engine** others depend on, not another dashboard users ignore.
- **Solve social friction, not just technical bugs:** reduce PR churn, eliminate "tribal knowledge" dependency, remove team debates about manifest quality.
- **Own the manifest boundary:** every manifest — hand-written, Helm, CDK, Pulumi, AI-generated — crosses this boundary. Yamlr owns it.
- **Fast and low-noise:** hooks must be <2s (warm cache), CI <30s. Precision (no false positives) is non-negotiable.
- **Deterministic always:** same input + version + config = identical output. Nondeterministic ordering is a bug.
- **Preserve comments:** YAML carries tribal knowledge. Default healing never drops comments.
